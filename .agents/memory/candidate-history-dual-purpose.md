---
name: Candidate history file dual purpose
description: StoredCandidateSet files now exist for every segment (VLM-resolved or hash-only), not just dropped ones — deferred recovery must filter by `dropped` and skip `checked` entries or it will re-verify/duplicate already-accepted segments.
---

`<matchJobId>_candidates_<segmentIndex>.json` files are written for every segment `resolveSegmentsWithVLM` finishes (accepted immediately, accepted after retries, or dropped) — not only dropped ones. This gives the compare UI full history (tried+rejected candidates plus never-checked pool alternates) for any segment, built via `buildCandidateHistoryEntry` in `server/candidate-recovery.ts`.

**Why:** the user wants to review VLM's rejected and never-tried candidates for segments that DID match, not only ones it gave up on — so the same file format now doubles as both "comparison history" (`dropped: false`) and "recovery queue" (`dropped: true`).

**How to apply:** `runDeferredRecoveryPass` (`server/deferred-recovery.ts`) must keep BOTH guards: skip entries where `dropped === false` (only genuinely-dropped ranges are recovery candidates), and skip individual `candidates[]` entries where `checked` is already `true` (the main pass already ran VLM on them — re-verifying wastes calls and risks a different verdict). Removing either guard risks re-verifying or duplicating already-accepted segments into the final result. `recoveredCandidateIndex` means "whichever candidate was ultimately used," set by the main pass the instant it accepts one (always the last entry in that segment's tried-candidates prefix), or later by deferred recovery if a dropped range gets recovered.

**Third purpose (hash-only, no VLM):** the compare-candidates UI is gated purely on "does a `StoredCandidateSet` file exist for this short-clip range" — it has no VLM-specific text. Since `resolveSegmentsWithVLM` returns early (writes nothing) when VLM is unavailable or original videos aren't retained, `buildHashOnlyCandidateHistoryEntry` writes a baseline entry for every segment right after hash-matching finishes (before the VLM block), using the same pool `groundMatchedSegments`/`groundMatchedSegmentsChunked` already return regardless of VLM. All its `candidates[]` are `checked: false` (nothing was actually verified) with `recoveredCandidateIndex: 0` marking the hash-accepted one — the UI already renders "not checked" + a separate "★ Used" badge independent of verdict, so this needed zero frontend changes. If VLM does run afterward, its richer per-segment write simply overwrites this baseline for that index (same file, last-write-wins) — no coordination flag needed between the two paths.
